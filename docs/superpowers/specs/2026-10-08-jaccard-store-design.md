# jaccard-store: design

Date: 2026-10-08. Status: approved in conversation, awaiting review of this
document.

## 1. Purpose

[jaccard-store-experiment](https://github.com/amber-store/jaccard-store-experiment)
showed that references kept as one pack file each, where a pack may lean on
one similar parent pack, capture 86 % of the sharing a fully deduplicating
store achieves. This project turns that into a service:

- a **server**, reachable over iroh, that keeps the packs in an S3 bucket and
  coordinates pushes and pulls without ever carrying pack bytes itself;
- a **client library and CLI** that push references from, and pull them into,
  a local [Amber-Store Core](https://github.com/amber-store/core) store;
- an **admin page** embedded in the server.

Success: `jaccard-store push` and `pull` round-trip references between two
local core stores through a server and a bucket, malformed uploads never
become visible, abandoned uploads and unreferenced packs leave the bucket,
and the admin page shows what the store holds and who put it there.

## 2. Decisions

### 2.1 Made by the owner

- Objects and keys are Amber-Store Core's (`github.com/amber-store/core`
  v0.10.0, hash-first keys), not rebma's.
- New private repository `amber-store/jaccard-store`, module
  `github.com/amber-store/jaccard-store`. No `internal/` packages.
- Pack data is object bytes back to back, compressed as **one zstd stream**.
- Access is **open**: whoever can dial the server's endpoint ID may push,
  pull, list and delete. The uploader's endpoint ID is recorded.
- The CLI works against a **local core store** (`packstore` + `refstore`);
  ingest and restore stay with core's own CLI.
- Server state is SQLite, with queries generated by **sqlc**.
- The server talks to S3 through the **AWS SDK for Go v2**; the client uses
  **plain `net/http`** against pre-signed URLs.
- The server is found by **endpoint ID alone**: it publishes itself through
  the relay infrastructure (pkarr/DNS) and mDNS, and clients resolve it the
  same way.
- **Validation**: the server downloads the new pack and walks its objects
  from the root. Only the new pack is walked; where a path crosses into the
  parent, the key's presence in the parent's index is enough, and the parent
  is assumed sound.
- CLI on `urfave/cli/v2`.

### 2.2 Made in design, accepted by the owner

- The index starts with an 8-byte magic and version before the key count.
- The sketch travels once, in `push-start`. For a base pack the server takes
  the sketch from the verified index, not from the client.
- The client decides between a base and a patch pack (`--min-dedup`, default
  0.5 of the reference's bytes held by the best candidate). The server
  enforces structure only.
- Every object the walk reads is hashed against its key, blobs included, and
  a pack may hold nothing the walk does not reach.
- The sharing figures of a patch pack (objects and bytes of the reference
  that the parent holds) are **reported by the client** and bounded by the
  parent's totals. They are statistics; nothing else depends on them.
- S3 objects of a collected pack are deleted one URL lifetime after the pack
  leaves the database, so URLs already handed out keep working.
- `ls` and `rm` exist beside `push` and `pull`.
- The CLI keeps a key file, so the uploader ID is stable.
- Two binaries: `jaccard-stored` (server) and `jaccard-store` (client).

## 3. Terms

- **Reference (ref)**: a name pointing at a root key.
- **Key set** of a root: the keys of every object reachable from it.
- **Base pack**: holds the whole key set of its root. Only base packs are
  parents.
- **Patch pack**: names one base pack as its parent and holds exactly the
  objects of its root's key set that the parent lacks. It may be empty, when
  the root itself is in the parent.
- **Pack of a root**: at most one verified pack exists per root key. Refs
  with the same root share it.
- **Sketch**: the 256 lowest keys of a key set by byte order (all of them
  when there are fewer). Keys lead with their hash, so this is a bottom-k
  MinHash sketch.

## 4. Pack format

A pack is two S3 objects.

### 4.1 Index

All integers big-endian.

```
magic    "JACIDX\x00\x01"                      8 bytes
count    number of entries                     8 bytes
entries  key[32] offset[8] length[4]           44 bytes each, ascending by key
```

`offset` and `length` locate the object's serialized bytes in the
**uncompressed** data stream. A valid index has canonical keys in strictly
ascending order, at most 2^24 entries, no length above core's
`amberpack.MaxPayload`, and entries that, ordered by offset, tile the stream
exactly: the first starts at 0 and each starts where the previous ends. The
uncompressed size of the data is therefore the sum of the lengths.

### 4.2 Data

A zstd stream that decompresses to the objects' serialized bytes back to
back, each once, in any order, with no framing. The window is at most
64 MiB. The data of an empty pack may be zero bytes long.

### 4.3 Names in the bucket

`<prefix>packs/<root hex>/<upload id>.idx` and `.data`. The upload ID keeps
concurrent uploads of one root apart and means nothing is ever renamed.

## 5. Protocol

ALPN `amber/jaccard-store/1`. Each request is one bidirectional QUIC stream:
the client writes one frame and closes its side, the server writes one frame
and closes. A frame is a 4-byte big-endian length and that many bytes of
CBOR, at most 16 MiB. A request is a map with `op` and the operation's
fields. A response carries either the result fields or
`error: {code, message}`.

Error codes: `bad_request`, `not_found`, `parent_gone`, `unknown_upload`,
`malformed_pack`, `internal`.

Names are validated with core's `reference.ValidateName`.

### 5.1 `push-start`

Request: `name`, `root`, `sketch` (ascending keys; the server uses the
lowest 256). A sketch that is empty, not strictly ascending, or longer than
4096 keys is a `bad_request`.

- If the root has a pack: the ref is pointed at it and the answer is
  `stored: true`.
- Otherwise: `candidates`, at most 3, nearest first. Each has `root`,
  `distance` (estimated Jaccard distance, 1 minus the similarity),
  `objects`, `bytes`, `data_size`, and `index_url` (pre-signed GET).

Nearest search: every base pack sharing a sketch key with the query is
counted through `sketch_keys`; the 16 sharing the most are scored with the
bottom-k estimate against their stored sketches; the best 3 with a
similarity above zero are returned. Ties go to the pack sharing more keys,
then to the lower root.

### 5.2 `push-upload`

Request: `name`, `root`, `parent` (root of a base pack, or absent),
`data_size` (bytes of the compressed data), `objects` (index entries),
`shared_objects`, `shared_bytes` (zero without a parent).

- If the root has a pack by now: as `stored` above.
- If `parent` is not a base pack the server knows: `parent_gone`. The client
  starts over.
- Otherwise the server records the upload and answers with `upload_id`,
  `deadline`, `index_url` (PUT), and for the data either `data_url` (one
  PUT) or `parts`: `part_size`, one PUT URL per part, and `complete_url`
  (the POST that completes the multipart upload).

Data above the part size (default 64 MiB) is uploaded in parts; the part
size grows so that there are at most 10,000. All URLs expire at the
deadline, one hour after issue by default.

The pre-signed part URLs come from the SDK's presign client; the completion
URL is signed with the SDK's SigV4 signer (`PresignHTTP`), since the presign
client has no call for it.

A pending upload counts as a reference to its parent, so the parent cannot
be collected while the upload is open.

### 5.3 `push-commit`

Request: `upload_id`. Only the endpoint that opened the upload may commit
it; for anyone else, and for an upload that has expired, the answer is
`unknown_upload`.

The server verifies the pack (section 6). On success it records the pack,
points the ref at it, and answers `ok`. If the root got a pack in the
meantime, the upload's objects are queued for deletion, the ref is pointed
at the existing pack, and the answer is `ok` as well. A pack that fails
verification is answered with `malformed_pack` and the reason, its objects
are queued for deletion, and the upload is forgotten. If S3 cannot be
reached, the answer is `internal` and the upload stays open for a retry.

### 5.4 `pull`

Request: `name`. Answer: `root` and `packs`: the ref's pack, then its parent
if it has one. Each has `root`, `objects`, `bytes`, `data_size`,
`index_size`, `index_url` and `data_url` (pre-signed GETs, valid for one
hour by default).

### 5.5 `list` and `delete`

`list`: `prefix`, `after`, `limit` (at most 1000). Answer: `refs` (`name`,
`root`) in name order, and `more`.

`delete`: `name`. Removes the ref; packs it leaves unreferenced are
collected.

Ref updates are unconditional: the last push wins.

## 6. Verification

At `push-commit` the server:

1. Checks with HEAD that both objects exist and have the declared sizes
   (index: 16 + 44 × `objects`).
2. Downloads and parses the index (section 4.1).
3. Downloads the data and decompresses it into a scratch file, refusing a
   stream that is shorter or longer than the index says.
4. For a patch pack, downloads the parent's index and checks that no key of
   the pack is in it.
5. Walks from the root, breadth first. A key in the pack is read from the
   scratch file, checked against its key by core's rule (BLAKE3 hash; the
   length field for `Blob` and `XattrSet`; the footprint for `Commit`), and
   its children (`fstree.ChildKeys`) are queued. A key not in the pack must
   be in the parent's index, and the walk stops there. A key in neither is
   a missing object.
6. Checks that the walk visited every entry of the index.

The root must be in the pack, unless the pack is empty and the root is in
the parent.

Anything that fails makes the pack malformed. Verifications run a few at a
time (default 2), which bounds the scratch space to the uncompressed size of
that many packs. The scratch directory is emptied at start.

## 7. Server

### 7.1 State

`<data>/server.key` (hex seed, created on first run), `<data>/store.sqlite`
(modernc SQLite, WAL), `<data>/scratch/`.

```sql
CREATE TABLE packs (
  id             INTEGER PRIMARY KEY,
  root           BLOB    NOT NULL UNIQUE,
  parent_id      INTEGER REFERENCES packs(id),   -- NULL: a base pack
  data_key       TEXT    NOT NULL,
  index_key      TEXT    NOT NULL,
  data_size      INTEGER NOT NULL,   -- bytes in S3
  index_size     INTEGER NOT NULL,
  objects        INTEGER NOT NULL,   -- objects in the pack
  bytes          INTEGER NOT NULL,   -- their uncompressed bytes
  shared_objects INTEGER NOT NULL,   -- of the ref, held by the parent
  shared_bytes   INTEGER NOT NULL,
  uploader       TEXT    NOT NULL,   -- endpoint ID
  uploaded_at    INTEGER NOT NULL,   -- unix seconds
  sketch         BLOB                -- base packs only
);
CREATE INDEX packs_parent ON packs(parent_id);

CREATE TABLE sketch_keys (            -- base packs only
  key     BLOB    NOT NULL,
  pack_id INTEGER NOT NULL REFERENCES packs(id) ON DELETE CASCADE,
  PRIMARY KEY (key, pack_id)
) WITHOUT ROWID;

CREATE TABLE refs (
  name       TEXT    PRIMARY KEY,
  pack_id    INTEGER NOT NULL REFERENCES packs(id),
  updated_by TEXT    NOT NULL,
  updated_at INTEGER NOT NULL
);
CREATE INDEX refs_pack ON refs(pack_id);

CREATE TABLE uploads (
  id             TEXT    PRIMARY KEY,
  name           TEXT    NOT NULL,
  root           BLOB    NOT NULL,
  parent_id      INTEGER REFERENCES packs(id),
  uploader       TEXT    NOT NULL,
  data_key       TEXT    NOT NULL,
  index_key      TEXT    NOT NULL,
  multipart_id   TEXT,
  data_size      INTEGER NOT NULL,
  objects        INTEGER NOT NULL,
  shared_objects INTEGER NOT NULL,
  shared_bytes   INTEGER NOT NULL,
  state          TEXT    NOT NULL,   -- 'pending' or 'verifying'
  issued_at      INTEGER NOT NULL,
  deadline       INTEGER NOT NULL
);

CREATE TABLE deletions (
  id           INTEGER PRIMARY KEY,
  object_key   TEXT    NOT NULL,
  multipart_id TEXT,                 -- set: abort this multipart upload
  not_before   INTEGER NOT NULL
);
```

`objects` and `bytes` of a pack come from its verified index. The sketch of
a base pack is the first 256 keys of its index.

### 7.2 Garbage collection

A pack is live while a ref points at it, a pack names it as parent, or an
open upload names it as parent. Whenever a ref moves or is deleted, or an
upload ends without a pack, the server deletes the packs that are no longer
live, repeating until none is left (a patch can free its base), in the same
transaction. Their S3 keys go to `deletions` with `not_before` one URL
lifetime ahead.

### 7.3 Sweeper

Every 30 seconds:

- An upload past its deadline and not being verified is forgotten: its
  multipart upload is queued for abort, and its two keys are queued for
  deletion now and again an hour later, because a PUT that began before the
  deadline can land after it.
- Due `deletions` are carried out. A row stays until S3 has confirmed.

Because every S3 delete goes through the queue and the queue is written in
the transaction that decides it, a crash leaks nothing. At start, uploads
left in `verifying` return to `pending`.

### 7.4 iroh

go-iroh v0.3.0. The endpoint is bound with the server key and the default
relays, waits to come online, advertises its interface addresses, publishes
itself through pkarr and answers mDNS, as `amber-serve` in transport-iroh
does. The endpoint ID is logged at start. Clients need nothing else.

### 7.5 Command

```
jaccard-stored --data DIR --s3-bucket NAME
               [--s3-prefix P] [--s3-endpoint URL] [--s3-region R] [--s3-path-style]
               [--admin-addr 127.0.0.1:8080]
               [--upload-timeout 1h] [--url-ttl 1h] [--part-size 64MiB]
               [--verify-jobs 2]
```

Credentials come from the SDK's default chain.

## 8. Statistics and the admin page

Per pack, and so per ref pointing at it:

| figure | from |
| --- | --- |
| objects, bytes of the ref | `objects + shared_objects`, `bytes + shared_bytes` |
| deduplicated | `shared_bytes` of the ref's bytes |
| parent objects, bytes the ref cannot reach | parent's `objects - shared_objects`, `bytes - shared_bytes` |

For the store:

- refs, base packs, patch packs, open uploads, queued deletions;
- bytes in S3: the sum of `data_size + index_size`;
- stored bytes: the sum of `bytes` over packs;
- logical bytes: the sum over refs of the bytes of the ref;
- deduplication rate: 1 − stored / logical;
- compression: S3 data bytes / stored bytes.

The admin listener serves a read-only JSON API and the page, on
`127.0.0.1:8080` unless told otherwise. It has no authentication; it is
bound to loopback for that reason.

```
GET /api/stats
GET /api/refs?prefix=&after=&limit=
GET /api/packs?after=&limit=
GET /api/packs/{root}        the pack, its refs, its children, its parent
GET /api/uploads
```

The page is plain HTML, CSS and JavaScript with no build step, embedded with
`go:embed`: an overview, the refs, the packs with a detail view (uploader,
time, sizes, parent, children, refs), and the open uploads.

## 9. Client

### 9.1 Push

1. Read the local ref, list its key set (`fstree.ReachableKeys`), sort it,
   take the sketch.
2. `push-start`. `stored` ends the push.
3. Fetch the candidates' indexes over HTTP. For each, the shared keys and
   their bytes are read off the index. The best candidate is the one sharing
   the most bytes.
4. Write the objects the best candidate lacks into a temporary data file
   through one zstd encoder, counting their bytes. If the candidate holds at
   least `--min-dedup` of the ref's bytes, that is the patch pack.
   Otherwise the shared objects are appended to the same stream and the
   pack is a base pack. With no candidate the pack is a base pack.
5. `push-upload`, then PUT the index and the data (parts in parallel, each
   a section of the file; the ETags go into the completion POST, whose
   answer is checked for an error body).
6. `push-commit`.

On `parent_gone` the push starts over once.

### 9.2 Pull

1. `pull`.
2. Fetch the pack's index, then stream its data through a zstd decoder,
   cutting objects in offset order and writing those the local packstore
   lacks with `PutVerified`.
3. `fstree.CheckComplete` on the root. If it is complete, the parent is not
   fetched: a client that already holds the parent's content never
   downloads it again.
4. Otherwise import the parent the same way and check again.
5. Set the local ref.

Object writes and the ref update go through core's write span and collector
span, as core's own CLI does, so a local GC running at the same time cannot
take them.

### 9.3 Command

```
jaccard-store --store DIR --server ENDPOINT_ID [--key FILE] COMMAND
  push REF [--as NAME] [--min-dedup 0.5]
  pull NAME [--as REF]
  ls [PREFIX]
  rm NAME
```

`--store` defaults to `$AMBER_STORE`, `--server` to `$JACCARD_SERVER`,
`--key` to `jaccard-store/client.key` in the user's configuration directory,
created on first use. The client resolves the server by ID through pkarr/DNS
and mDNS and uses the relay as fallback path.

## 10. Layout

```
sketch/     bottom-k sketch and the Jaccard estimate
packfile/   index and data: encode, decode, lookup, the pack builder
verify/     the walk of section 6
wire/       ALPN, frames, messages
db/         schema, migrations, queries; db/dbq is sqlc's output
bucket/     S3: object calls, pre-signing, multipart
node/       iroh: key file, serving endpoint, announcing, dialing
server/     the protocol handler, garbage collection, the sweeper
admin/      the HTTP API; admin/web is the page
client/     push, pull, list, delete
cmd/jaccard-stored/
cmd/jaccard-store/
```

Go through the flake's dev shell, as in the sibling repositories.

## 11. Testing

Tests are written before the code they cover.

- `sketch`, `packfile`, `wire`, `db`: unit tests, including the nearest
  search and the liveness rules.
- `verify`: one test per way a pack can be malformed: bad magic, unsorted
  or duplicate keys, entries that do not tile, a stream too short or too
  long, an object that does not hash to its key, a missing child, an entry
  the walk does not reach, a key also in the parent, a missing root.
- End to end, in one process: a server with real iroh endpoints on loopback
  (relays and discovery off, direct addresses given through the library) and
  an in-process S3 fake, driven through the client library. Covered: a base
  pack; a patch pack; a root that is already stored; a ref that moves and
  the collection that follows; an upload that expires; a malformed upload
  refused and removed; the multipart path with a small part size; two
  clients pushing one root at once; a pull that skips the parent.
- `admin`: the API through `httptest`.
- One opt-in test against a real S3 endpoint named in the environment.

## 12. Out of scope

Authorization; repacking or re-basing existing packs; ranged reads of pack
data; resumable uploads; rebuilding the database from the bucket; more than
one server on a bucket; more than one level of parents.

## 13. Known limits

- Access is open, so anyone who learns the endpoint ID can fill the bucket.
- The sharing figures are the client's word.
- The database is the only record of refs and of which pack leans on which.
  It has to be backed up; the bucket alone does not describe the store.
- A verification needs scratch space for the uncompressed pack.
- A pull that needs the parent downloads all of it.
